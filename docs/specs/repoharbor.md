## 2. 目标与范围

### 背景

需要把其他账号的公开 GitHub 仓库完整镜像到本地服务器，按计划拉取更新，并提供一个在手机、平板和桌面浏览器上都能使用的管理界面。系统面向单管理员、局域网自托管场景，不修改 GitHub 侧的任何内容。

### 目标

- 管理公开 GitHub 仓库的本地 bare mirror。
- 支持新增、删除、修改仓库配置，仓库 URL 创建后不可修改。
- 支持每个仓库独立设置 cron 同步计划、立即同步、暂停和恢复。
- 提供响应式 Web 管理端，包含仓库列表、同步状态、仓库详情、只读代码浏览、提交历史和差异查看。
- 使用单管理员密码保护管理功能。
- 使用 Docker 部署，前端构建后由后端静态托管。

### 非目标

- 私有仓库、GitHub Token、SSH 凭据。
- 在 GitHub 上创建、修改、删除仓库或 Fork。
- 在线编辑代码、提交、推送。
- Issues、Pull Requests、Releases、Wiki。
- Git LFS 对象下载。
- 多用户、多租户、权限隔离。
- 全仓库代码搜索。
- 通知、邮件、Webhook、统计图表。
- 内置备份和恢复功能。
- 对外开放 API。
- GitHub Enterprise、其他 Git 托管平台、SSH 地址。
- 原生 App、PWA、离线模式。
- 迁移已有本地 clone 或已有管理系统的数据。

## 4. 行为要求与约束

### R-001：仓库接入与校验

- 参与者或触发方：管理员。
- 前置条件与输入：管理员已登录；输入 `https://github.com/<owner>/<repo>` 形式的公开仓库 URL；运行环境可访问 GitHub。
- 必须满足的行为：规范化 URL；校验主机必须是 `github.com`；使用 `git ls-remote` 在 15 秒内验证仓库可访问且为公开仓库；拒绝重复 URL、私有仓库、无效地址和不支持的托管平台。
- 输出或状态变化：创建仓库记录，初始状态为 `pending`，并加入首次镜像队列。
- 边界与失败行为：校验失败时不创建记录，返回明确错误；不得向 GitHub 写入任何内容。

### R-002：首次镜像

- 参与者或触发方：首次同步任务。
- 前置条件与输入：仓库记录状态为 `pending`；目标目录不存在或为空。
- 必须满足的行为：使用 `git clone --mirror` 拉取全部分支、标签和提交历史；先写入临时目录，成功后再移动到最终目录；读取默认分支和仓库大小。
- 输出或状态变化：本地 bare mirror 建立；仓库状态更新为 `success`；记录最后同步时间和下次同步时间。
- 边界与失败行为：失败时清理临时目录，状态记为 `failed`，保存错误摘要；首次镜像失败按 R-006 重试。

### R-003：定时同步

- 参与者或触发方：调度器。
- 前置条件与输入：仓库已启用且存在本地 mirror；到达 `next_sync_at`。
- 必须满足的行为：调度器每 30 秒检查一次到期仓库；每个仓库同一时间只允许一个同步任务；全局并发数为 2–3；同步完成后按仓库间隔计算下一次时间。
- 输出或状态变化：状态依次变为 `syncing`、`success` 或 `failed`；更新 `last_sync_at` 和 `next_sync_at`。
- 边界与失败行为：服务重启后不补跑错过任务；恢复后按当前时间重新计算下一次同步时间。

### R-004：手动同步

- 参与者或触发方：管理员。
- 前置条件与输入：仓库存在且当前没有运行中的同步任务。
- 必须满足的行为：立即加入同步队列；暂停状态下的仓库仍允许手动同步；同步过程与定时同步一致。
- 输出或状态变化：产生一条 `manual` 类型的同步记录；界面通过 SSE 收到状态变化。
- 边界与失败行为：同一仓库已有同步任务时返回 `409 Conflict`，不重复执行。

### R-005：暂停与恢复

- 参与者或触发方：管理员。
- 前置条件与输入：仓库存在。
- 必须满足的行为：暂停只停止定时调度，不强制终止正在运行的同步；恢复后重新计算 `next_sync_at`；暂停期间仍允许手动同步。
- 输出或状态变化：`enabled` 切换为 `false` 或 `true`；列表和详情显示暂停或启用状态。
- 边界与失败行为：重复暂停或恢复视为幂等操作，不报错。

### R-006：同步失败重试

- 参与者或触发方：同步引擎。
- 前置条件与输入：同步因网络超时、连接失败、临时服务不可用等可重试错误失败。
- 必须满足的行为：自动重试最多 3 次，间隔分别为 1、5、15 分钟；每次尝试单独记录；仓库不存在、URL 无效、远端历史改写等不可重试错误不自动重试。
- 输出或状态变化：重试记录标记为 `retry`；最终成功则状态为 `success`，最终失败则状态为 `failed`。
- 边界与失败行为：重试期间不阻塞其他仓库；重试耗尽后等待下一次计划任务或管理员手动触发。

### R-007：远端历史改写保护

- 参与者或触发方：同步引擎。
- 前置条件与输入：同步前已存在本地 mirror；远端发生 force push、分支删除或历史重写。
- 必须满足的行为：在应用新 refs 前进行非快进和删除检测；检测到历史改写或 ref 删除时保留现有本地 refs，不自动覆盖；记录 `REMOTE_REWRITTEN` 错误并提示需要手动强制重新镜像。
- 输出或状态变化：仓库状态为 `failed`；本地 mirror 保持同步前状态。
- 边界与失败行为：不得自动重置本地 mirror；只有管理员显式执行 R-008 才能重建。

### R-008：强制重新镜像

- 参与者或触发方：管理员。
- 前置条件与输入：仓库存在；管理员在确认框中确认会删除当前本地镜像。
- 必须满足的行为：停止该仓库的同步任务；删除当前本地 mirror；重新执行首次镜像；保留历史同步记录并新增一条 `force_reset` 记录。
- 输出或状态变化：本地 mirror 被远端当前状态替换；仓库状态更新为 `success` 或 `failed`。
- 边界与失败行为：GitHub 原仓库不受影响；操作前必须显示破坏性确认。

### R-009：删除仓库

- 参与者或触发方：管理员。
- 前置条件与输入：仓库存在；管理员确认删除；仓库当前没有运行中的同步任务。
- 必须满足的行为：删除本地 mirror 目录；删除仓库配置和相关管理记录；显示仓库大小供确认；不修改 GitHub。
- 输出或状态变化：仓库从列表消失；磁盘空间释放。
- 边界与失败行为：同步运行中拒绝删除；GitHub 原仓库保持原样；删除后只能通过重新添加 URL 恢复。

### R-010：修改仓库配置

- 参与者或触发方：管理员。
- 前置条件与输入：仓库存在。
- 必须满足的行为：允许修改显示名称、cron 同步计划、启用/暂停状态和备注；URL 创建后不可修改；同步计划使用标准 5 段式 cron，并提供每 15 分钟、每 30 分钟、每小时、每 12 小时、每天的预设；修改计划后重新计算 `next_sync_at`。
- 输出或状态变化：配置更新；列表和详情立即反映新配置。
- 边界与失败行为：显示名称为空时回退为 `owner/repo`；备注长度上限为 1000 个字符。

### R-011：首次管理员设置

- 参与者或触发方：首次访问的用户。
- 前置条件与输入：系统中不存在管理员账号。
- 必须满足的行为：仅允许通过首次设置页面创建管理员；管理员用户名固定为 `admin`；设置不少于 12 个字符的密码；密码使用 Argon2id 哈希保存；设置成功后关闭首次设置入口。
- 输出或状态变化：管理员账号创建；用户进入登录状态。
- 边界与失败行为：已存在管理员时拒绝重复设置；不得提供默认密码。

### R-012：登录、会话与登出

- 参与者或触发方：管理员。
- 前置条件与输入：管理员账号已存在。
- 必须满足的行为：用户名和密码登录；连续失败 5 次后限流 15 分钟；登录成功后创建服务端会话；会话有效期 7 天；Cookie 使用 `HttpOnly`、`SameSite=Lax`；所有写操作要求 CSRF Token；支持主动登出。
- 输出或状态变化：会话写入 SQLite；受保护接口可访问；登出后会话失效。
- 边界与失败行为：未登录访问受保护接口返回 `401`；登录失败不泄露账号是否存在。

### R-013：访问控制

- 参与者或触发方：所有 HTTP 请求。
- 前置条件与输入：请求到达后端。
- 必须满足的行为：`/api/v1/health`、首次设置、登录接口和静态前端资源允许匿名访问；其余 API 必须验证会话；未登录页面访问跳转登录页。
- 输出或状态变化：已认证请求正常处理；未认证请求返回 `401` 或重定向。
- 边界与失败行为：不得通过静态资源路径绕过 API 鉴权。

### R-014：仓库列表

- 参与者或触发方：管理员。
- 前置条件与输入：已登录；至少存在一个仓库或进入空状态。
- 必须满足的行为：展示仓库名称、owner/repo、同步状态、最后同步时间、下次同步时间、最近错误和磁盘占用；支持按名称/owner/URL 搜索、按状态筛选、按名称或最后同步时间排序；默认每页 20 条。
- 输出或状态变化：列表反映当前数据库状态；同步状态通过 SSE 更新。
- 边界与失败行为：无仓库时显示引导添加仓库的空状态；移动端使用卡片布局，桌面端使用表格布局。

### R-015：只读代码浏览

- 参与者或触发方：管理员。
- 前置条件与输入：仓库已完成首次镜像。
- 必须满足的行为：展示分支和标签列表；默认选中默认分支；支持目录树、文件内容查看和单文件下载；文本文件最多内联显示 2 MiB；二进制文件或超限文件只显示元信息并允许下载；LFS 指针文件显示提示；禁止路径穿越；不提供编辑功能。
- 输出或状态变化：页面展示指定 ref 和路径的内容。
- 边界与失败行为：ref、路径或文件不存在时返回 `404`；无权访问或路径非法时返回 `400`。

### R-016：提交历史与差异

- 参与者或触发方：管理员。
- 前置条件与输入：仓库已完成首次镜像；已选择分支或标签。
- 必须满足的行为：默认展示当前选中分支的完整提交历史；提交列表按每页 50 条加载，前端使用虚拟滚动或分页按需请求；提交详情展示作者、时间、提交信息和变更文件；支持查看单次提交的 unified diff；超大 diff 截断并提供下载或继续加载提示。
- 输出或状态变化：提交列表和详情正常展示。
- 边界与失败行为：不存在的 commit 返回 `404`；不提供跨分支混合时间线视图。

### R-017：README 渲染

- 参与者或触发方：管理员。
- 前置条件与输入：仓库根目录存在 README 文件。
- 必须满足的行为：识别 `README.md`、`README.markdown` 或 `README`；使用安全的 Markdown 渲染；清理脚本和危险 HTML；相对链接和相对图片解析到仓库文件接口；外部图片按浏览器默认行为加载。
- 输出或状态变化：仓库详情页展示渲染后的 README。
- 边界与失败行为：README 不存在时不显示该区块；渲染失败时回退为纯文本。

### R-018：同步记录与日志

- 参与者或触发方：同步引擎和管理员。
- 前置条件与输入：同步任务开始或结束。
- 必须满足的行为：永久保留每次同步的时间、触发方式、结果、耗时和错误摘要；完整 Git 输出写入滚动日志文件，只保留最近 20 次或 30 天；数据库保存最近 16 KiB 日志摘要；同步记录列表分页展示。
- 输出或状态变化：仓库详情可查看同步历史和错误信息。
- 边界与失败行为：日志文件清理不得删除数据库中的同步记录。

### R-019：磁盘占用展示

- 参与者或触发方：管理员。
- 前置条件与输入：已登录；数据目录可读取。
- 必须满足的行为：每次同步后更新仓库大小；系统页面展示数据目录总占用和所在文件系统剩余空间；文件系统使用率达到 85% 时显示警告；不设置硬性配额。
- 输出或状态变化：列表、详情或系统状态页展示最新占用数据。
- 边界与失败行为：无法读取磁盘信息时显示“未知”，不阻塞同步和浏览。

### R-020：服务重启与任务恢复

- 参与者或触发方：服务启动流程和调度器。
- 前置条件与输入：服务重启或进程恢复。
- 必须满足的行为：把重启前处于 `syncing` 的记录标记为中断失败；跳过停机期间错过的定时任务；为所有启用仓库按当前时间重新计算 `next_sync_at`；不自动补跑。
- 输出或状态变化：调度器恢复运行；界面显示中断记录和新的下次同步时间。
- 边界与失败行为：不得在启动时同时触发大量同步任务。

### R-021：数据备份说明

- 参与者或触发方：管理员和部署者。
- 前置条件与输入：使用 Docker 部署。
- 必须满足的行为：文档说明 `/data` 是唯一需要备份的数据目录；备份前应停止容器或执行 SQLite 一致性备份；备份内容包括 SQLite 数据库、bare mirror 和日志目录。
- 输出或状态变化：提供可执行的备份和恢复步骤。
- 边界与失败行为：第一版不提供内置备份按钮或定时备份。

### R-022：Docker 运行约束

- 参与者或触发方：部署者。
- 前置条件与输入：已安装 Docker 和 Docker Compose。
- 必须满足的行为：容器监听 8080；`/data` 挂载为持久卷；运行用户为非 root；提供健康检查；前端静态文件由 Go 二进制内嵌并提供；同一数据卷只运行一个实例。
- 输出或状态变化：容器启动后可通过 `http://<host>:8080` 访问。
- 边界与失败行为：数据卷不可写或端口被占用时启动失败并输出明确日志。

### 相关约束

- 仅支持 `https://github.com/<owner>/<repo>` 形式的公开仓库。
- 不使用 GitHub API 或任何 GitHub 凭据。
- 单实例部署，不支持多个副本同时写同一个 SQLite 文件。
- 运行环境必须安装 Git；Docker 镜像必须包含 Git 和 CA 证书。
- 支持现代 Chrome、Safari、Edge、Firefox；最小布局宽度 360px。
- 管理界面默认简体中文。
- SQLite 使用 WAL 模式、外键约束和 `busy_timeout`。

## 5. 关键决定

### D-001：项目名称与位置

- 状态：已确认
- 结论：项目名为 RepoHarbor，路径为 `/app/project/RepoHarbor`。
- 理由：名称简短，语义贴合“把仓库停靠到本地”；路径由用户指定。
- 考虑过的备选：GitDock、MirrorNest、ForkDock。
- 未采用原因：用户选择 RepoHarbor。
- 影响范围：文档标题、代码仓库名、Docker 镜像名和页面品牌。

### D-002：本地镜像而不是 GitHub Fork

- 状态：已确认
- 结论：只把目标仓库克隆为本地 bare mirror，不在 GitHub 账号下创建 Fork。
- 理由：不产生额外 GitHub 仓库，不需要写权限，风险最低。
- 考虑过的备选：GitHub Fork 后克隆；仅纳管已有本地 clone。
- 未采用原因：用户明确只需要本地镜像。
- 影响范围：R-001、R-002、D-003。

### D-003：仅管理公开仓库

- 状态：已确认
- 结论：只支持公开 GitHub 仓库，不支持私有仓库、Token 或 SSH 凭据。
- 理由：目标是保存其他账号的公开仓库，不需要凭据管理。
- 考虑过的备选：支持私有仓库并保存 Token；使用 SSH 部署密钥。
- 未采用原因：用户明确暂不支持私有仓库。
- 影响范围：R-001、R-012、相关约束。

### D-004：配置型仓库管理

- 状态：已确认
- 结论：新增、删除、修改只针对仓库配置和本地副本，不编辑代码；仓库 URL 创建后不可修改。
- 理由：把“仓库管理”和“代码托管”分开，避免第一版变成在线 IDE。
- 考虑过的备选：在线编辑文件并提交；允许修改 URL 并原地重拉。
- 未采用原因：用户明确只管理配置；URL 变更通常代表不同仓库，容易混入无关历史。

## 8. 技术设计

### 8.1 总体架构

RepoHarbor 是单进程应用：

- Go 后端提供 REST API、SSE、静态前端和调度器。
- React 前端构建为静态文件，通过 `//go:embed` 嵌入 Go 二进制。
- SQLite 保存元数据、同步记录、设置和会话。
- Git 仓库以 bare mirror 形式保存在数据目录。
- Docker 镜像只包含 Go 二进制、Git、CA 证书和时区数据。

请求路径：

```text
Browser -> Go HTTP server
             ├── /api/v1/*        REST + SSE
             ├── /assets/*        embedded frontend
             └── /                SPA fallback
Go scheduler -> git CLI -> /data/repos/*.git
Go store     -> SQLite   -> /data/repoharbor.db
```

### 8.2 模块职责

| 模块 | 职责 | 主要依赖 |
|---|---|---|
| `cmd/repoharbor` | 读取配置、初始化数据库、启动 HTTP 服务和调度器 | `config`、`store`、`api`、`scheduler` |
| `internal/api` | 路由、请求校验、OpenAPI、SSE、静态文件 | `auth`、`store`、`gitrepo` |
| `internal/auth` | 首次设置、密码哈希、登录、会话、CSRF、限流 | `store` |
| `internal/gitrepo` | mirror 管理、refs、文件树、文件、历史、diff、大小统计 | `os/exec`、文件系统 |
| `internal/scheduler` | 到期检查、worker pool、重试、暂停/恢复、重启恢复 | `store`、`gitrepo` |
| `internal/store` | SQLite 连接、sqlc 查询、事务、迁移 | `modernc.org/sqlite`、`sqlc`、`goose` |
| `internal/config` | 环境变量、路径、监听地址、日志级别 | 标准库 |
| `web` | React 管理端、代码浏览、响应式布局 | React、Vite、TanStack Query |

### 8.5 Git 与镜像设计

- 目录：`/data/repos/<owner>__<repo>.git`
- 首次镜像：`git clone --mirror <url> <tmpdir>`，成功后原子移动到最终目录。
- 增量同步：抓取远端 refs 到临时 refs 命名空间，比较旧 refs 与新 refs；只有全部 ref 都是快进更新时才应用到本地 refs。
- 历史改写检测：使用 `git merge-base --is-ancestor <old> <new>` 判断快进；分支删除或非快进视为 `REMOTE_REWRITTEN`，保留本地 refs。
- 文件浏览：`git --git-dir=<mirror> ls-tree`、`git cat-file`、`git show <ref>:<path>`。
- 提交历史：`git log --format` + `--skip` / cursor 分页。
- 差异：`git diff <parent> <sha>` 或 `git show --format= --patch <sha>`。
- 大小统计：同步后对 mirror 目录执行 `du -sb`。
- 不递归子模块；LFS 指针按普通文本显示并提示。

### 8.6 调度与并发

- 调度器每 30 秒扫描 `enabled=1 AND next_sync_at <= now` 的仓库。
- worker pool 并发数 3。
- 每个仓库使用进程内互斥锁，防止定时、手动、重试重叠。
- 同步开始前在事务中把 `status` 更新为 `syncing`，避免重复领取。
- 同步结束后写入 `sync_runs`，更新仓库状态和时间。
- 可重试错误：网络超时、连接失败、临时 DNS 失败。
- 不可重试错误：仓库不存在、URL 无效、历史改写。
- 重启恢复：把 `running` 记录标记为 `failed`，所有启用仓库 `next_sync_at = now + interval`。

### 8.7 认证与会话

- 首次设置：仅当 `admin_users` 为空时开放。
- 密码：Argon2id，随机盐，最少 12 字符。
- 会话：随机 32 字节 token，数据库只保存 SHA-256 哈希；Cookie 名 `repoharbor_session`，`HttpOnly`、`SameSite=Lax`、`Path=/`。
- CSRF：双提交 Cookie 或服务端 token；所有 `POST`、`PATCH`、`DELETE` 要求 `X-CSRF-Token`。
- 登录限流：按 IP 记录失败次数，5 次失败后锁定 15 分钟。
- 登出：删除会话记录并使 Cookie 失效。

### 8.8 前端设计

- 路由：
  - `/setup` 首次设置
  - `/login` 登录
  - `/` 仓库列表
  - `/repositories/:id` 仓库详情
  - `/repositories/:id/tree/:ref/*` 文件浏览
  - `/repositories/:id/commits/:ref` 提交历史
  - `/repositories/:id/commit/:sha` 提交详情与 diff
  - `/settings` 系统设置
- 数据层：TanStack Query；SSE 收到事件后失效相关 query。
- 代码高亮：Shiki；diff：`diff2html`；Markdown：`react-markdown` + `remark-gfm` + `rehype-sanitize`。
- 表单：`react-hook-form` + Zod。
- 响应式：
  - 桌面：左侧导航 + 主内容区。
  - 平板：可折叠侧栏。
  - 手机：顶部栏 + 抽屉/底部导航；列表使用卡片；文件树和 diff 使用全宽布局。
- 空状态、加载骨架、错误提示和破坏性操作确认统一组件化。

### 8.9 Docker 设计

- `Dockerfile` 多阶段：
  1. `node:24-bookworm-slim`：构建 `web/dist`。
  2. `golang:1.27-bookworm`：编译 Go 二进制，复制 `web/dist` 供 `embed`。
  3. `debian:bookworm-slim`：安装 `git`、`ca-certificates`、`tzdata`、`curl`；创建非 root 用户；复制二进制；暴露 8080。
- `docker-compose.yml`：
  - 服务名 `repoharbor`
  - `ports: ["8080:8080"]`
  - `volumes: ["./data:/data"]`
  - `environment: REPOHARBOR_ADDR=:8080`, `REPOHARBOR_DATA_DIR=/data`, `TZ=Asia/Shanghai`
  - `restart: unless-stopped`
  - healthcheck 调用 `/api/v1/health`
- 数据卷权限：文档要求宿主机 `data` 目录对容器运行用户可写；推荐 UID/GID 可配置。
